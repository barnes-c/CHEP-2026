Both the Virtual infrastructure layer (OpenStack resources, metadata, lifecycle) and the Physical infrastructure layer (hardware inventory, network registration, lifecycle records) are managed through Terraform/OpenTofu. Custom providers handle resource provisioning, inventory registration, and certificate management in a unified way, replacing the manual and error-prone steps previously required across these two layers.

The CM Layer still has the full responsibility for the runtime configuration through the existing Puppet and Foreman tooling. Rather than replacing or duplicating these systems, the framework treats them as the source of truth for host-level configuration. 

The key design property is a single source of intent stored in VCS, from which provisioning, classification, and registration are all derived. This directly addresses the multiple stores of state mentioned in Chapter~\ref{infra} and reduces boundary drift across all integration points shown in Figure~\ref{fig:framework-layers}.

\subsection{State and Drift Model}

One of the benefits of using Terraform/OpenTofu is its ability to detect drift by comparing declared intent against the actual state of infrastructure resources. When a plan is executed, the tool reconciles three representations: the declared configuration, the stored state file, and the real-world resource state queried through provider APIs. Any deviation is surfaced explicitly before changes are applied.

Within the proposed framework, this ability is used to correct drift by running scheduled plan operations through CI/CD pipelines. Drift introduced outside the framework, e.g. through manual interventions during incidents, becomes visible at the next pipeline execution, giving operators an explicit and auditable view of inconsistencies. Detected drift is corrected by re-applying the declared state through the standard workflow.

\subsection{Provisioning Workflow}

Provisioning happens via a CI/CD workflow. An Operator commits changes to their infrastructure repository. The CI/CD pipeline executes validation and a plan operation, producing an auditable view of intended changes. If approved, the pipeline applies the changes. Terraform/OpenTofu provisions cloud resources and registers the host with supporting services through custom providers. The instance boots, cloud-init executes the bootstrap logic, and the Puppet agent performs its first catalog request. From this point, configuration convergence is managed by CM and is outside the framework's control. Figure~\ref{fig:provisioning-seq} illustrates this workflow.

Updates follow the same \texttt{plan/apply} cycle. The framework does not implement continuous reconciliation; drift is detected through plan output and corrected by re-applying the declared state.
